## 1. Problem statement

The capstone needs one read-only web app that demonstrates the Elasticsearch practicals on a real dataset. The existing 13-practical material is spread across synthetic indices and disconnected exercises. The real `gujrat_rera_data` index (17,271 projects, 279.1 MB, ES 8.19.23) is a better substrate: real text, real facets, real dirty data, and real non-indexed objects.

The three surfaces that matter most:

- Search by `project_name` (also `promoter_name` and `reg_no`), with highlighting and prefix suggestions.
- Filters on `district`, `taluka`, `project_type`, `project_status`, `price`, dates, and scrape status.
- Project Detail showing the five large non-indexed objects, including `Project Profile`, as readable section cards.

Every screen shows the exact Query DSL, the server `took` time, and local wall-clock time so the practical lesson is visible.

## 2. What makes this cool

- Real Gujarat RERA data, not synthetic employees/products.
- Project Detail renders five large `enabled:false` objects Elasticsearch cannot index: Project Profile, Project Summary, Promoters, Progress & RERA Actions, More Projects by The Same Developer. That is the "wait, ES cannot query this?" moment.
- The yellow single-node cluster with an unassigned replica is a built-in ops lesson, not a bug.
- Dirty district/taluka values turn data quality into a visible, concrete panel.
- The app teaches while it works: every response carries `query_used`, `es_took_ms`, and `wall_ms`.

## 3. Constraints

- ES `8.19.23`; pin `elasticsearch>=8.19,<9` and `AsyncElasticsearch`.
- Single index `gujrat_rera_data`; `dynamic:false`; five `enabled:false` objects.
- Read-only; `ALLOW_WRITES=false`; no hidden write endpoints.
- Allowed non-mutating calls only: GET APIs, `POST /_pit`, `DELETE /_pit`, `POST /_analyze`, `POST /_ingest/pipeline/{id}/_simulate`.
- No scripts, `script_fields`, `runtime_mappings`, `regexp`, or leading wildcard in any interactive path.
- `size` max 100; `from + size > 10000` rejected with `invalid_request`.
- `price` is a keyword: `term`, `prefix`, and `terms` only; never numeric `range` or numeric sort.
- Dates use `dd-MM-yyyy`; every range query passes `"format": "dd-MM-yyyy"`.
- List/search endpoints use `_source` includes and never return the five disabled objects; only detail loads them.
- One FastAPI app, one query module, one HTML page. No DB, auth, Docker, build step, or framework.
- Never log or return credentials; the config endpoint exposes only the host.
- Server `took` and local wall-clock timings are labeled separately.

## 4. Premises

1. Success is a demoable teaching artifact covering 12 of 13 practicals (P12 geo is N/A).
2. The real index beats synthetic data.
3. Read-only is a feature, not a limitation.
4. The "whoa" is Project Detail plus the query-used/timing panel, not the search table.
5. One-command local run beats deployment polish.

## 5. Approach

Approach A: vertical slices, one small app. Build each tab end-to-end in phase order. One `queries.py`, one `routes.py`, one `app.js`, one `styles.css`. Effort S/M, risk low. The capstone payoff is a working demo, not a modular framework.

Approach B (modular capability registry) and Approach C (query cookbook first) were considered and rejected. Approach A was approved in office hours, and the file structure was kept as-is in engineering review D1.

## 8. Final architecture

### 8.1 Request flow

```text
Browser (app.js)
  |  fetch + AbortController (20s)
  v
FastAPI routes.py
  |  validate params / recursive allowlist / size caps
  v
queries.py (pure builders)          es_client.py
  |  query bodies                    |  AsyncElasticsearch singleton
  |                                  |  capability flags
  |                                  |  PIT session registry (UUID -> pit_id, TTL)
  v                                  v
Elasticsearch 8.19.23 (gujrat_rera_data only)
```

### 8.2 PIT lifecycle

```text
Browser              routes.py            es_client.py              ES
  |--open PIT------------>|                    |                     |
  |                       |--open_point_in_time-------------------->|
  |<--session_id----------|<-------------------|<--pit_id-------------|
  |--next(session_id)---->|                    |                     |
  |                       |--search(pit,sort)->|-------------------->|
  |<--hits+new pit_id-----|<-------------------|<--search_after-------|
  |--export CSV----------->| generator owns PIT |                     |
  |                       |--finally close PIT---------------------> |
  |--close(session_id)---->|--delete_pit---------------------------> |
```

Rules: `search-after` consumes the browser session id from the registry; update stored `pit_id` from every response; refresh `keep_alive=2m`; registry TTL must be lower than 2m; missing/expired PIT maps to `invalid_request: session expired` with reopen guidance; CSV export owns a separate PIT and closes it in `finally`.
